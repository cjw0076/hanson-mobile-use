## 2. Hardened Safety & Zero-Plaintext Boundaries

### 2.1 Blind Credential Vault (`vault://` Separation)
1. **Encryption at Rest**: User secrets are stored with `AES-256-GCM` (`AndroidKeyStore` hardware-backed key on Android devices; `PBKDF2WithHmacSHA256` fallback on headless JVM hosts).
2. **LLM Prompt Isolation**: The prompt composer (`@vault`), `/vault` slash handler, `vault_list_handles`, and `NotetakerScratchpad` see only opaque handles (`vault://naver_login`), category badges (`LOGIN`, `PAYMENT`, `IDENTITY`), and masked previews (`ha••@naver.com`).
3. **Blind Injection & Recovery Guard**:
   - `vault_blind_inject` decrypts secrets strictly inside [`AgentToolExecutionHarness.kt`](../app/src/main/java/com/hanson/mobileuse/agent/AgentToolExecutionHarness.kt) right before Accessibility injection and runs every tool output through `redactSensitiveText(...)`.
   - [`ActionTrajectoryVerifierAndHealer.kt`](../app/src/main/java/com/hanson/mobileuse/agent/ActionTrajectoryVerifierAndHealer.kt) explicitly excludes `vault_blind_inject` from `UID-2000` shell text injection recovery so plaintext credentials are never placed on shell command lines or logs.

### 2.2 Non-Bypassable Human Takeover (`AWAITING_TAKEOVER`)
- `FinancialAndTakeoverGuard.assessBeforeAction(...)` scans UI trees and window titles before mutating GUI tools.
- When **CAPTCHA / Cloudflare Turnstile / human-verification** (`HighStakesKind.CAPTCHA_BOT_GATE`), **2FA / biometric / secure keypad** (`HighStakesKind.TWO_FACTOR_OR_BIOMETRIC`), or **protected surfaces** (`HighStakesKind.SECURE_SURFACE_BLOCKED`) appear, the engine halts immediately in `AgentRunStatus.AWAITING_TAKEOVER` and surfaces `HumanTakeoverBannerCard`.
- Automated solving, clicking through, computing, or bypassing bot challenges is strictly forbidden. Execution resumes only after explicit user confirmation (`직접 완료 · 에이전트 재개`), which recaptures the post-takeover snapshot before continuing.

### 2.3 High-Stakes Financial & Price-Drift Gate
- Even when `unrestrictedAutonomousMode == true`, checkout/order/transfer/booking commits (`FINANCIAL_COMMIT`) and price increases relative to prior confirmed quotes (`PRICE_DRIFT_ALERT`) force an explicit single-shot `InlineApprovalPromptCard`.
- High-stakes financial approvals suppress `"항상 허용"` ("Always Allow") so subsequent transactions cannot silently inherit blanket approval.
